1496|Day 35 — AI Testing: Assertions, Throughput and Little’s Law

1497|1. UAT in the AI testing lifecycle

1498|UAT validates real business flows with business users. It should not be the first stage for heavy automation, load testing, or deep engineering. Before UAT, core functionality, AI-quality checks such as hallucination checks, integration testing, and basic performance benchmarking should be available.

1499|Typical flow: Functional testing → AI quality/integration testing → Performance testing → UAT → Production monitoring. In real projects, stages can overlap. UAT may run in parallel with performance testing because of schedule or budget pressure. Automation may be complete while full CI/CD implementation happens after UAT.

1500|Interview line: “I follow the planned sequence but allow overlap when needed. Core functionality, integrations, AI-quality checks, and baseline performance should be available before UAT.”

1501|2. Dynamic values and correlation

1502|A product name returned by a product-list request is dynamic because it can change based on the request or database. A fixed response field is static. Login data and request parameters should be parameterized instead of hard-coded so different virtual users can use different data.

1503|Correlation extracts a value from one response and uses it in a later request:

1504|Product-list response → JSON Extractor → c_product_name → place-order request uses ${c_product_name}

1505|Common dynamic values include product name, product ID, order ID, and user ID. Parameterization supplies different input values; correlation passes generated response values between requests.

1506|3. Assertions: HTTP 200 is not business success

1507|HTTP 200 only means the request was processed at the HTTP level. An AI agent can return 200 and still say, “Which product would you like me to order?” The request is technically successful, but the order business flow failed.

1508|Use a JMeter Response Assertion to check the expected business result. Useful checks include response text, response code, and response headers. For an order, assert text such as “order placed successfully,” confirmed status, payment method, shipping address, or order details. Prefer a reliable condition and use Contains when appropriate.

1509|Every important request should have an assertion. In a 10,000-transaction test, assertions can identify 100 business failures automatically instead of requiring manual response inspection.

1512|Day 35 — Performance Control and Feasibility

1513|4. Constant Timer versus Constant Throughput Timer

1514|A Constant Timer adds a fixed delay. A timer placed at the top of a thread group can affect every request under that scope; one inside a transaction affects only that transaction. This delay acts as think time.

1515|A Constant Throughput Timer receives a target rate, such as 50 requests per minute, and JMeter calculates the delay needed to approach it. Example: 4.6 requests per second × 60 = 276 requests per minute. Run a throughput test long enough for it to settle—Vishnu suggested roughly four or five minutes, or at least two to three minutes.

1516|Constant Timer: fixed delay → indirectly controls throughput. Constant Throughput Timer: target rate → JMeter calculates delay.

1517|5. Workload modelling and AI limits

1518|Business flows normally have different usage levels. For example, place order, browse products, and update account may run together, and login may exist in all three thread groups. If the overall login SLA is 20 TPS, giving 20 TPS to every group could create about 60 TPS. Divide the target according to the expected distribution.

1519|A workload model can use production logs, business expectations, SLA targets, user distribution, model rate limits, and token limits. For AI testing, this prevents unrealistic traffic and helps control token consumption.

1520|6. Little’s Law

1521|Little’s Law helps calculate users, throughput, or think time and can be used before the JMeter script is complete:

1522|User count = Throughput × (total response time + total think time) ÷ transactions per user cycle

1523|Keep units consistent. If throughput is per minute, response and think time must be in minutes; if throughput is per second, use seconds.

1524|Inputs: user count, throughput, number of transactions, total response time, and total think time. In the class example, approximately 20.2 per minute, three transactions, six seconds of response time, and one second of think time produced roughly 2.5 users for a target near 60 per minute, so three users were used.

1525|Feasibility example: one transaction taking one second with a target of 200 TPS requires about 200 users. If the environment or license allows only 100 users, the target is not feasible. Little’s Law can reveal this during test planning, even before scripting.

1526|Interview line: “I use the workload model and Little’s Law to check whether users, response time, transaction mix, and throughput are feasible before execution.”

1527|7. What can fail

1528|·       HTTP 200 but business failure: add a business-level Response Assertion.

1529|·       Hard-coded data: use CSV parameterization and correlation.

1530|·       Throughput above SLA: divide traffic across thread groups.

1531|·       Unstable throughput: run longer and ignore the warm-up period.

1532|·       Wrong result: keep all formula units consistent.

1533|·       Impossible target: calculate required users before running the test.

1534|Quick check

1535|Why can HTTP 200 still mean order failure? What is the difference between the two timers? Should every thread group receive the full shared login SLA? What values are required by Little’s Law?

1536|Expected answers: HTTP 200 is transport success only; one timer adds fixed delay while the other targets a rate; shared SLA must be distributed; and the formula needs users, throughput, transactions, response time, and think time.

1538|Day 36 — JMeter Synchronization, Controllers, and Token Logging

1539|This class connects AI performance testing with operational analysis. The examples and numbers below are class examples; actual limits must come from the project requirement.

1540|1. AI testing is coupled

1541|Traditional performance testing mainly asks whether the application handles load. AI testing also checks behaviour, cost, tokens, and production operation. These areas are connected. If token usage is reduced from 150 words to 100 words, cost may improve, but the answer may become incomplete and answer relevancy may fall.

1542|Behaviour testing ↔ Performance/cost testing ↔ Production monitoring → change in one area → regression in the other areas

1543|Whenever the model, prompt, token limit, parameters, tool response, or important configuration changes, repeat the behaviour cases that could be affected. If only a safe configuration change was made and it cannot affect behaviour, full retesting may not be needed—but the impact should be considered.

1544|2. AI performance testing is usually scaled down

1545|The performance team may run a broad test with a mock model in a larger performance environment. The AI tester focuses on the real model and AI path, often in staging or pre-production with fewer users. Vishnu’s example was a performance test with 100 users and an AI test with about 10 users. This is a class guideline, not a universal rule.

1546|Traditional performance test: broad flow + mock AI + larger environment. AI performance test: real model + AI tools + smaller controlled load.

1547|The goal is to observe real token usage, tool calls, latency, and behaviour without creating unnecessary model cost. Do not assume that a mock performance result proves the real AI path is healthy.

1548|3. Synchronizing Timer

1549|A Synchronizing Timer makes a group of virtual users wait and then releases them together. Without it, users progress independently. Both tests may show the same TPS, but the traffic pattern is different.

1550|Normal test: User 1, User 2, User 3 → progress naturally. Synchronizing Timer: User 1 + 2 + 3 wait → all start together.

1551|Normal independent traffic is usually more realistic. A synchronized release is useful for a spike test or a situation where many users really act at the same instant, such as a token-generation event. It should not automatically be used for every performance test.

1552|The timer’s “number of simulated users to group by” controls the batch size. For example, grouping by 10 releases users in groups of 10. A timeout controls how long JMeter waits for the group. If the users do not arrive within that time, JMeter releases the users it has.

1553|4. Controllers

1554|Controllers control when and how samplers or requests execute.

1555|·       Loop Controller: repeats the requests inside it. If login is set to five loops, each user performs login five times before moving on.

1556|·       If Controller: runs its requests only when a condition is true, such as an approved message or a valid order ID.

1557|·       Throughput Controller: controls the percentage or number of executions across a group of requests.

1558|Example: if login should be 70% of the traffic and product list 30%, place each flow under a Throughput Controller with those percentages. The percentages come from the workload model.

1559|5. Throughput Controller versus Constant Throughput Timer

1560|A Constant Throughput Timer targets the rate of an individual request or transaction. A Throughput Controller distributes execution across a group of requests. The timer controls how often; the controller controls which requests receive the traffic.

1561|Constant Throughput Timer → target rate for a request. Throughput Controller → percentage distribution between flows.

1563|6. Capture token and latency values

1564|The AI response may contain input tokens, output tokens, total tokens, estimated cost, latency, order ID, and a message. Use JSON Extractors to capture these fields into JMeter variables.

1565|AI response → JSON Extractor → input_token, output_token, total_token, cost, latency, order_id → write to CSV or create a report

1566|These fields must be returned by the application API or obtained through an approved monitoring tool. They are not created by JMeter. The same API response can be inspected using JMeter, LoadRunner, StormRunner, or NeoLoad.

1567|7. BeanShell and JSR223

1568|A BeanShell PostProcessor can write extracted variables to a file. A JSR223 PostProcessor can run a Groovy script for the same type of logging and report generation. A script can write only failures, add a serial number, include an error message, or create an HTML report.

1569|Extract variables → PostProcessor script → CSV/log/HTML report → analysis

1570|Use the JMeter log while testing. Warnings may be acceptable, but errors must be investigated. If a file is not created, the log can show the path or script problem. Keep file paths and variable names correct.

1571|8. Analyse anomalies

1572|A report may show most transactions using 2,000–2,300 tokens, while a few use 8,000. Those outliers can increase cost and latency. If the response time crosses the SLA, use the order ID, product, tool trace, and message to investigate the specific transaction.

1573|·       High input tokens: too much product or tool data was sent to the model.

1574|·       High output tokens: the model produced an unusually long answer.

1575|·       High latency: extra tokens, slow retrieval, repeated tools, or another backend component may be involved.

1576|·       Missing order ID or zero tokens: the order may have failed, tracing may be incomplete, or the response path may be wrong; investigate rather than assuming the cause.

1577|9. Architecture solution: summarize once and reuse

1578|If product details are 50 to 200 words, passing the full text every time can increase input tokens. A better design is to summarize the product once when it is added, store the short summary in a normal database, and retrieve that summary whenever the AI needs it.

1579|Product added → Create short AI summary once → Store summary in SQL database → Retrieve summary for future AI requests → Lower input tokens, cost, and latency

1580|The detailed product description can still be kept for the user interface. This avoids paying for the same summarization repeatedly.

1581|10. SQL database versus vector database

1582|Use SQL when the data is structured and the query is clear, such as product ID, order ID, or customer ID. Use a vector database when users search by meaning or natural language and the system must find similar content.

1583|Structured relation and exact filter → SQL database. Meaning-based document search → Vector database.

1584|Vector storage normally requires converting data into embeddings before storing it, which adds cost and maintenance. AI testers do not normally build embeddings or databases, but they should understand the purpose so they can identify the likely owning team and retest after a fix.

1585|11. Tester to solution recommender

1586|The class gave four steps:

1587|·       Identify the problem through testing.

1588|·       Understand the real root cause and business impact.

1589|·       Use architecture and technology knowledge to propose a solution.

1590|·       Record the root cause and fix so the organisation can reuse that knowledge.

1591|This is the difference between only reporting a failure and thinking like a test architect. Speak with the developer or data engineer after a bug is fixed so you understand why it happened.

1662|The local demonstration used command windows, so closing a command window could stop a service. In a real environment, services normally run in the background. Installation paths vary by machine; do not blindly copy another person’s path.

1663|3. Connect Prometheus as a data source

1664|Grafana cannot create data by itself. It reads data from a configured source. For this setup, Prometheus was added as the data source using the Prometheus server URL. Select the correct authentication option, save the connection, and use Save and Test. A successful Prometheus API query confirms the connection.

1665|Grafana → Add data source → Prometheus URL → Save and Test → Query data

1666|Grafana can also connect to SQL, InfluxDB, Graphite, Azure Monitor, and other data sources. A dashboard can contain panels from more than one source if the organisation configures them.

1667|4. Create a Grafana dashboard

1668|A panel is one visualisation, such as a time-series graph, number, bar chart, or table. First test the Prometheus query in Prometheus. Then use the working query in Grafana. Choose the best visualisation, set units such as MB, name the panel, and save it to a dashboard.

1669|Prometheus query → Grafana panel → Choose graph or stat → Set units → Save dashboard → View several metrics together

1670|Useful AI panels include total tokens, input tokens, output tokens, latency, error count, CPU, memory, and throughput. A dashboard can be reused for different applications or releases. Variables can allow the user to select an instance or environment and update several panels.

1671|5. Auto refresh and sharing

1672|Set dashboard auto-refresh while a test is running so graphs update automatically. After the test, stop auto-refresh and select the time range that contains the run. Share the dashboard only with people who have access. For a stakeholder report, a screenshot with the important peak marked and explained may be more useful than an unannotated link

1673|6. JMeter data reaches Grafana through Prometheus

1674|JMeter does not send data directly to Grafana in this setup. JMeter captures values, a JSR223 script sends custom metrics to Pushgateway, Prometheus stores them, and Grafana reads them through the Prometheus data source.

1675|JMeter → JSR223/Groovy → Pushgateway → Prometheus → Grafana

1676|If you want JMeter response time or LLM token values in Grafana, push each value as a metric. JMeter Summary Report values are not automatically available in Grafana. A server-side or tool-specific script can be used when the load test runs elsewhere.

1678|7. Production monitoring does not require JMeter

1679|JMeter simulates users for testing. In production, real users generate traffic. A service or server-side script can capture application metrics and push them to Prometheus. Therefore, Grafana and Prometheus can monitor production without JMeter. JMeter is only one possible producer of data.

1680|Prometheus or its exporters need access to the application or server being monitored. For a local demonstration, the application and Prometheus were on the same laptop. In a real environment, install or configure the exporter/service on the correct server and follow the organisation’s network and security rules.

1681|8. Alerts

1682|Grafana can alert when a Prometheus query crosses a threshold. Examples include memory above 90%, token usage above 10,000, high latency, or an error count above an agreed limit. Alerts can appear in Grafana or be sent to tools such as Slack when integrations are configured.

1683|Metric query → Threshold rule → Alert condition → Notification → Action

1684|Thresholds must come from requirements or SLAs. An alert should lead to an action: investigate a cost spike, scale resources, check a failing tool, or stop a dangerous run. AI monitoring can detect unusual token usage that may indicate a prompt problem, repeated calls, or suspicious activity.

1685|9. Retention and time range

1686|Prometheus stores time-based data according to its retention configuration. Retention may be based on time, such as seven or thirty days, or storage size. Old data is deleted when the retention rule is reached. If a dashboard cannot show an older test, check the selected time range and retention policy before assuming the data was never collected.

1687|10. Grafana versus ELK

1688|ELK is commonly used for log collection and log investigation. Grafana is mainly used here for metric dashboards, trends, panels, and alerts. They can complement each other: use metrics to see when and how badly a system changed, then use logs and traces to investigate the individual request.

1689|11. What can fail

1690|·       Grafana is installed but no data source is configured.

1691|·       Prometheus, Pushgateway, exporter, or the application is not running.

1692|·       The Prometheus URL or authentication setting is wrong.

1693|·       The query works in Prometheus but the Grafana panel uses the wrong metric name or unit.

1694|·       JMeter values are never pushed, so Grafana shows no custom token data.

1695|·       The dashboard is not refreshed, so the tester sees old data.

1696|·       Retention removed older test results.

1697|·       A threshold alert has no owner or action.

1698|·       A metrics problem is investigated without checking logs or traces.

1699|Interview answer

1700|“I configure Prometheus as the Grafana data source, create panels for latency, tokens, errors, CPU, and memory, and enable refresh during a test. JMeter pushes custom AI metrics through JSR223 and Pushgateway into Prometheus. I use Grafana alerts for SLA or token thresholds and investigate anomalies with the time range, logs, and traces. In production, a server-side service can push metrics without JMeter.”

1702|Day 39 — LangSmith Tracing, Agents, Tools, and MCP

1703|This class introduced LangSmith as a monitoring and tracing tool for AI agents. It also clarified how an agent, an LLM, tools, and MCP work together. The key tester skill is to use trace evidence to explain what happened, where time was spent, and which tool or model step failed.

1704|1. Connect an application to LangSmith

1705|Create or sign in to a LangSmith account, create a project or agent trace, generate an API key, and configure the application. The application configuration normally needs the LangSmith API key, project name, endpoint, and tracing enabled. The key is usually configured once and should be stored securely, not pasted into public code.

1706|LangSmith account → API key/project → Application configuration → Enable tracing → Restart/setup application → Generate a request → Trace appears in LangSmith

1707|For the class shop application, setup scripts handled some installation. In another project, the required package must be installed on the server where the application runs. Configuration names and setup steps can vary by application architecture, so select the correct “trace an existing application” option and follow the current documentation.

1708|2. What a trace shows

1709|A trace records the chain of work behind one user action. For an order, it may show the first model request, search-products tool, product-availability tool, place-order tool, later model requests, token usage, cost, inputs, outputs, and execution time.

1710|User request → Agent → LLM decision → Tool 1 result → LLM decision → Tool 2 result → Final answer

1711|If an action takes 8.9 seconds and the stakeholder requires 5 seconds, a total response time is not enough to find the solution. The trace shows whether the model request, retrieval, tool, or final response consumed the time. In the example, tools took very little time and the model calls were the larger part. Possible improvements include reducing unnecessary input context, reducing output size, or reducing token usage.

1712|3. Use traces to create test cases

1713|LangSmith can show the application’s available tools and the tools invoked for a particular request. A small application may already have about 25 tools. Do not create only one test per tool. Vishnu’s class guidance was at least four cases per tool, producing roughly 100 cases for 25 tools. The real number depends on risk and requirements.

1714|Useful cases include:

1715|·       Positive request that should invoke the tool.

1716|·       Missing or invalid input.

1717|·       Tool returns no data or an error.

1718|·       Wrong tool selection or wrong tool sequence.

1719|·       Boundary and ambiguous wording.

1720|·       Security, permission, and business-rule cases.

1721|Attach the trace ID, trace link, screenshots, input, output, and tool response to a defect. A statement such as “the bot gave a wrong answer” is weak evidence. A trace can show whether the model selected the wrong tool, the tool returned wrong data, or the final model changed correct data.

1722|4. Agent, LLM, and tool responsibilities

1723|The LLM is the reasoning and language component. It decides which tool is needed and produces the final wording. The tool is normally code or an API that performs the real action. The agent is the program that connects the user, LLM, and tools and controls the sequence.

1724|User/UI → Agent code → LLM → tool request → Agent executes tool → result returns to LLM → final answer

1725|The LLM cannot directly execute an API. The agent code receives the LLM’s tool request, calls the correct tool, sends the result back to the LLM, and continues the workflow. In a real project these pieces may be in one file or multiple services; the logical responsibilities remain the same.

1726|5. RAG and agents

1727|RAG retrieves information using a tool and gives that information to the LLM. An agent adds decision-making and actions. Therefore, an agent can include RAG, but a simple RAG flow is not necessarily a complete action-taking agent.

1729|6. What MCP means

1730|MCP means Model Context Protocol. It is a standard structure that describes tools, their purpose, and their parameters so an LLM-connected agent can understand what tools are available. MCP is not the actual tool implementation. The tool code exists in the backend; MCP provides the standard description and connection structure.

1731|MCP server → tool name + description + parameters → LLM understands capability → Agent code executes backend tool

1732|Without a shared tool definition, developers may need to update the LLM instructions whenever a new tool is added. With MCP, the new tool can be added using the standard structure, so the agent can discover its purpose without changing unrelated instructions. This reduces the risk of modifying a tested system prompt.

1733|7. Custom and pre-built MCP servers

1734|A custom MCP server contains an organisation’s own tool definitions. A pre-built MCP server provides common capabilities, such as GitHub actions or file-system actions. The developer installs or connects the MCP server to the agent. Authentication may still be needed for an external service such as GitHub or a cloud platform.

1735|MCP does not remove the need for an agent. The agent remains the mediator between the LLM and the tool code. MCP standardizes how tool capabilities are exposed.

1736|8. MCP testing focus

1737|·       The tool description accurately explains the real capability.

1738|·       Required parameters and data types are correct.

1739|·       The LLM selects the correct tool for the user intent.

1740|·       The agent executes the selected tool and returns the result.

1741|·       A new tool becomes available without breaking existing tools.

1742|·       Permissions and authentication prevent unauthorized actions.

1743|·       Tool errors produce a safe, understandable response.

1744|·       The trace shows the tool, inputs, output, and sequence.

1745|9. LangSmith versus Grafana

1746|LangSmith is especially useful for AI-agent traces: model calls, tool calls, inputs, outputs, tokens, cost, and step-by-step execution. Grafana is useful for customizable dashboards combining application and infrastructure metrics such as CPU, memory, latency, tokens, and error trends. They complement each other rather than replacing each other.

1747|LangSmith can also support evaluators by connecting a judge model and applying a high-level evaluation. DeepEval and LangSmith evaluators do not replace manual review for high-risk behaviour. Select the tool and metric based on the project.

1748|10. n8n and the tester’s scope

1749|A drag-and-drop tool such as n8n can connect systems such as Teams and Outlook quickly. Large organisations may prefer custom code for control and scalability, while smaller teams may use visual builders. As a tester, focus on how to test the workflow: trigger, tool selection, authentication, data mapping, failure handling, and final result. Do not drift from testing into claiming development expertise.

1750|11. What can fail

1751|·       Wrong API key, project, endpoint, or disabled tracing means no trace appears.

1752|·       The application is not restarted after configuration changes.

1753|·       A developer adds a tool but does not expose it to the LLM.

1754|·       The LLM selects the wrong tool or sends incorrect parameters.

1755|·       The tool returns wrong data and the final answer sounds confident.

1756|·       A slow model call is blamed on the tool without checking the trace.

1757|·       MCP description and backend tool behaviour do not match.

1758|·       A trace is not attached to a defect, so developers cannot reproduce the issue.

1759|Interview answer

1760|“I use LangSmith to trace an agent end to end. I inspect each model call, tool selection, tool response, token count, cost, and execution time. I use the trace to create tool-level test cases and to identify root cause. MCP provides a standard description of tools, while the agent code still executes them. I test tool discovery, parameters, permissions, failures, and regression when a new tool is added.”
